Current State
現況盤點（經 codebase 驗證）
以下皆為實際讀檔確認，非推測。標 ✓ 為已存在能力，標 ✗ 為缺口。

前端 bkw（Angular 17）

  • Standalone components + Signals（computed/effect）+ NgRx facade + Transloco i18n。
  • 存款 UI 在 libs/ui/v3/h5/page/wallet/deposit/，v3 為現行版本。
  • Step2＝deposit-entry：讀 paymentInfo，按 bankGroupType（本地銀行/第三方/加密）分組、濾掉 INACTIVE。✗ 無「上次使用」高亮。
  • Step3（既有精簡流程）＝deposit-quick（1761 行）：已有 defaultPaymentType 預選、setDefaultPromotion 自動套用相容優惠、amountOptionList 快選金額、depositDataCache 暫存選擇。
  • API 由 DepositService 統一：getDepositPaymentInfo、getDepositSetting、deposit3rdParty、deposit、getPendingDeposit。
  • ✓ PaymentMethodStatusType.MAINTENANCE=0、method 的 isMaintain、channel 的 maintainStart/EndTimestamp、isRecommend 皆已在 model。
  • ✗ depositDataCache 是 signal(null) 記憶體暫存，不持久化（跨登入/裝置即失）。

後端 bkw-pg（Java 21）

  • 非 Spring Boot：傳統 Servlet + MyBatis + Oracle；Redis(Redisson) + Caffeine + Kafka + Togglz。單體 WAR。
  • 存款頁資料：GET /api/wv/v1/payment/getDepositPaymentInfo → BackendAPIWV3 / BTPaymentBO.getDepositPaymentInfo → PaymentDisplaySettingCache.getDepositSetting(account)。
  • ✓ 此 API 已按玩家過濾（幣別/站台/status/白黑名單/VIP/is_fe_display_condition 會查玩家歷史存款次數與累計金額）→ 代表「在這支 API 讀玩家存款歷史」的路徑現成。
  • ✓ MoneyTransaction 有 user_id / to_payment_type / to_bank_id / amount / status / create_time → 可推導最近/最常用方式與金額。
  • ✗ 無專用 Player Preference 表/欄位；快選金額 integer_amount_json 為 per-channel 全局配置（SpeedDeposit / PaymentDisplaySetting），非個人化。
  • 維護：現況為 BankType 層級（checkPaymentMethodIsMaintain()）→ 目前「隱藏」；顯示層 status 為 INVISIBLE(-1)/INACTIVE(0)/ACTIVE(1)。
  • 存款成功寫入點：PaymentGatewayServlet callback（/pg/CallBackRelay*）驗簽後更新 MoneyTransaction.status=SUCCESS → 這是偏好「寫入」的掛點。
⚠ 狀態語意需對齊：後端 status（-1 INVISIBLE / 0 INACTIVE / 1 ACTIVE）與前端 PaymentMethodStatusType（-1 INACTIVE / 0 MAINTENANCE / 1 ACTIVE）數值語意不一致。前端另有 isMaintain boolean。實作維護顯示前，務必先確認 getDepositPaymentInfo API 層對 paymentMethodStatus / isMaintain 的實際對應與填值邏輯。
Foundation
① User Profile — 記住上次/常用存款偏好
這是 ②③ 多數功能的共同地基。目標：後端能回傳玩家「上次方式 / 上次金額 / 最常用金額 / 是否首存」，前端據此預選預填。

🎨 設計 易

  • 定義「上次使用」與「最常存」兩種標籤的視覺（原型：綠框 + 標籤）；兩者可能衝突，需定優先序（建議：預設帶「上次」，金額 chip 標「最常用」）。
  • 啟用門檻：原型定「最常用金額」需 ≥3 筆存款紀錄，未達則顯示平台熱門金額——設計需涵蓋「無歷史」的 fallback。
  • 隱私：共用裝置上是否顯示上次金額，需產品拍板（可只預選不顯示數字）。

🗄️ 後端 中 — 兩個方案

方案 A · 讀時計算（建議先做）

  • 在 getDepositPaymentInfo（BTPaymentBO）查 MoneyTransaction：該玩家最近一筆 SUCCESS 存款的方式/金額，+ GROUP BY amount 取最常用。
  • 零 schema 變更，重用既有 per-player 查詢模式（is_fe_display_condition 已在查歷史）。
  • 結果以 Redis 快取（key=accountId，存款成功時失效），避免每次進頁多打 DB。
  • 風險低、可回滾。

方案 B · 反正規化欄位（量大再做）

  • 新增欄位（Account 表或新 PLAYER_DEPOSIT_PREFERENCE 表）：last_payment_type / last_bank_id / last_amount / updated_at。
  • 寫入掛在 PaymentGatewayServlet 存款成功 callback。
  • 讀取最快，但 Oracle 需手寫 DDL（無 JPA 自動 migration）+ DAO/XML + DBA review。
✓建議：Phase 0 先做方案 A（讀時計算 + Redis），最快解鎖 ②③ 的所有預選/預填；若監測到查詢負載才升級到方案 B。

② Step2 — 方式選擇（最大流失點）
改動落在 deposit-entry.component.ts（+ payment-method-item）。三個子項：預選上次方式、維護中明示、FTD 引導。

2-1 預選上次使用方式 前端易 · 後端依賴①

  • 設計：上次方式加綠框 + 「上次使用」標籤；底部 CTA 改「繼續用 E-wallet」；每方式加一行速度/用途說明。
  • 前端：deposit-entry 依後端 lastBankTypeId 對 orderedPaymentTypes 做高亮與置頂。純展示層，無流程風險。
  • 後端：由 ① 提供 last 方式即可，無額外工作。

2-2 維護中明示 + 預計恢復 前端中 · 後端中

✓資料模型已就緒：method 有 isMaintain + paymentStart/EndTimestamp；channel（DepositSettingModel）有 isMaintain + maintainStart/EndTimestamp；PaymentMethodStatusType.MAINTENANCE 存在。ETA 不需新欄位。
  • 設計：維護方式保留顯示、半透明 + 「維護中」標籤 + 不可點；用 maintainEndTimestamp 顯示「Back at 15:00」；自動高亮下一可用方式（「推薦替代」）。
  • 前端：目前 deposit-entry 只特判 INACTIVE，需新增 MAINTENANCE 分支：渲染標籤、disable 點擊、讀 timestamp 顯示 ETA。
  • 後端：關鍵是「顯示而非隱藏」——現況維護中的 BankType 被 checkPaymentMethodIsMaintain() 濾除。需讓 getDepositPaymentInfo 回傳維護項並帶 isMaintain=true + 時間戳，而非過濾掉。需確認狀態語意對齊（見現況盤點警示）。

2-3 首次存款（FTD）引導 前端中 · 後端易

  • 設計：頂部提示「建議新玩家從 E-wallet 開始」；「新手推薦」醒目標籤；此邏輯只顯示一次，之後切為「預選上次」。
  • 前端：依後端 isFirstDeposit 顯示提示條 + 用既有 isRecommend 呈現推薦標籤。
  • 後端：由 ① 一併回傳 isFirstDeposit（無成功存款紀錄）；isRecommend 已存在。
Prototype P2
③ Step3 — 表單精簡（第二大流失點）
關鍵前提：既有 deposit-quick 已實作單頁精簡的一大半。工作重心是「補完 + 串接①偏好」，而非重寫。
★待團隊確認（最高優先）：deposit-quick 目前被品牌設定 gate 住（isShowQuickDepositEntry / paymentDisplayFlags），而 deposit-entry 點擊後是導向分型別頁（deposit-thirdparty / deposit-localbank / deposit-crypto）。需先確認本品牌現行 Step3 走哪條，才能決定是「啟用 quick」還是「改造分型別頁」。

3-1 自動帶入上次設定 前端中 · 後端依賴①

  • 設計：進表單即帶入上次方式/type/channel/金額，用緊湊摘要列呈現，右側「更換」。
  • 前端：deposit-quick 已有 defaultPaymentType + depositDataCache 還原 + 自動優惠；只需把「來源」從記憶體暫存改為①的後端 last 值，並預填 amount。上次通道停用時，既有邏輯已會 fallback 到 list[0]。
  • 後端：由 ① 提供 last type/channel/amount。

3-2 統一「支付 + 優惠」Sheet · 優惠自動套用 前端中 · 後端無

  • 設計：移除表單頂部強制選優惠；填完金額後自動套用最優惠並顯示「已自動套用」；切換支付方式時同一 Sheet 內即時更新相容優惠。
  • 前端：setDefaultPromotion 已做「自動套用預設/相容優惠」；PromotionSelectComponent 底部 Sheet 已存在。整併成「支付+優惠」單一 Sheet 屬中度重構（合併兩個既有元件的互動）。
  • 後端：相容性資料 bonusTemplateList[].awardingBankTypes 已隨 API 回傳，無需後端改動。

3-3 不相容衝突引導 前端中 · 後端無

  • 設計：選到不相容組合時彈出引導 Sheet，說明「[支付] 不支援 [優惠]」，給兩條出路（換相容優惠 / 換支付方式），不強迫。
  • 前端：相容性判斷已有（bonusTemplateForPaymentMethodExist() / awardingBankTypes），需新增衝突引導 Dialog 元件與觸發時機。
  • 後端：無（資料已足夠）。
