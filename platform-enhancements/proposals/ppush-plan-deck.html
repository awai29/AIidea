平台與可行性

玩家在哪些平台？推播送得到嗎？

Web Push 的可行性高度取決於平台。站台幾乎全是行動裝置（99.7%）——其中 Android 一步授權、免安裝即可推播；iOS 則需引導「加入主畫面」變 PWA 才收得到。

平台可行性關鍵條件
Android / Chrome✅ 完全可行一般瀏覽器分頁就能用，一步授權、無需安裝——這是最強的案例。
Desktop（Chrome / Edge / Firefox）✅ 可行瀏覽器原生支援 Web Push，但桌機僅占 0.3% — 非主力。
iOS / Safari⚠️ 有條件必須「加入主畫面」變成 PWA，一般 Safari 分頁完全收不到推播，需額外引導。
※ 行動裝置占 99.7%（桌機僅 0.3%，可忽略）；行動裝置內依解析度統計 Android : iOS ≈ 77.5 : 22.5，且多為高密度（3x）螢幕。→ 幾乎是純手機盤口：約 3/4 玩家走 Android，一步授權即可推播；約 1/4 iOS 需引導加入主畫面。
關鍵限制

推播的開關，握在使用者手上

推播是否送達由使用者決定。玩家一旦拒絕瀏覽器通知，功能就完全失效；Chrome 被「封鎖」後更是再也彈不出系統視窗。關鍵不是「能不能推」，而是「怎麼讓玩家願意開」。

✕ 太早 / 隨機跳出系統視窗
一進站就彈窗 → 玩家反射性封鎖 → 永久失效。封鎖後任何授權呼叫都被瀏覽器靜默忽略，這個玩家再也救不回來。
✓ 在對的時機，軟性引導
先用站內軟性詢問 → 說明好處後再請求 → 同意率高、保留退路。「稍後」不等於「永不」，絕不硬碰系統封鎖。
對的時機 ▸ 💰 存款成功後 🏆 中獎 / 領獎時 🎁 領取優惠時 ⚽ 關注賽事開賽前
對的時機 · 軟性引導

什麼是「對的時機」？

把授權邀請包裝在玩家的成就感與情緒高峰時刻，而不是一進站就打擾——同意率最高，也最不傷體驗。

場景 A連續登入 3 天
把授權邀請包裝在成就時刻 — 高轉換率。
場景 B首次申請出金後
出金代表信任，順勢提供「到帳通知」—— 見右圖實例。
場景 C首次贏錢後
情緒高峰 — 轉換率最高的時機之一。
場景 D首次存款成功後
GA 數據：42% 用戶首存後即流失 — 信任感最高、建立習慣的最佳視窗。

技術實施 · 各端作業

設計、前端、後端各自要做什麼？

P1 首發垂直切片：首次出金 / 首頁 banner 觸發 → soft-ask 邀請 → 當場系統授權 → granted 綁 token；且啟動不再自動跳提示。P1 首發P2 次期P3 後期

🎨 設計
  • P1soft-ask 邀請彈窗 V2 / V3 視覺與文案（出金版 · 首頁 banner 版）
  • P1標準 / 隱私模式通知樣式規範（標題·內文·圖示·圖片·按鈕）
  • P3設定頁通知區塊、分類偏好中心
  • P3已封鎖（denied）解鎖引導畫面
💻 前端 · Angular
  • P1移除「啟動自動請求權限」→ 僅 granted 才靜默刷新 token
  • P1權限狀態機（能力偵測 iOS/Safari/PWA ＋ 三時機重讀）
  • P1soft-ask 服務 ＋ 頻率控管（出金 1 次 · banner 7 天冷卻、上限 3 次）
  • P1兩觸發點接線：首次出金成功 ＋ 首頁 banner
  • P2到帳事件渲染、payload 契約落實
  • P3設定頁通知區塊 ＋ 分類偏好中心
⚙️ 後端 · Java 負擔小
  • P1token 綁定 API ✅ 已存在、免改（Redis 多裝置 · 30 天 TTL）
  • P1首次出金旗標 isFirstWithdrawal（低工 · 出金筆數＝1）
  • P2payload 契約（notificationType·title·body），會簽 FCM 發送服務

⚠ 跨團隊待敲定：pilot 品牌（DB TRACKINGSETTING type=7）· notificationType 整數／字串 · 追蹤機制（GA.gtag vs EventQueue）。  ✦ P1 後端幾乎免改 — token API 已現成、出金旗標低工，主要工作量落在前端與設計。
